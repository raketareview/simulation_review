**5. class Field**

- Карта должна иметь возможность быть созданной с произвольными размерами.

Карта содержит в себе фиксированные размеры, поэтому становится неуниверсальной- нельзя создать игровые конфигурации с картами разных размеров
```java
public class Field {
  private final int WIDTH = 15;
  private final int HEIGHT = 10;

  public Field() {...}
}

//ПРАВИЛЬНО:
public class Field {
  public final int width;
  public final int height;

  public Field(int width, int height) {...}
}
```
Фиксированные размеры могут быть у шахматной доски(8x8) или игры крестики-нолики(3x3).  
То есть в тех играх, где размер игрового поля жестко фиксирован правилами.  
Здесь размеры должны приниматься в конструктор, чтобы можно было создавать карту произвольных размеров.

- Карта не должна хранить запись координата-null, то есть пустые ячейки. 

Иначе теряется все преимущество, которое дает HashMap для хранения сущностей
```java
public Field() {
  for (int row = 0; row < HEIGHT; row++) {
    for (int col = 0; col < WIDTH; col++) {
      cells.put(new Coordinate(col, row), null);  <-- ЗАПОЛНЯЕТ КАРТУ ПУСТЫМИ ЯЧЕЙКАМИ
    }
  }
}
```
Фактически, тут Map становится аналогом обычного массива, только хуже, бесполезно забивая память.
Например, есть игровая доска 100x100 и в ней одномоментно находится общим числом 150 разных существ: камней, травы, зайцев и т.д.
Тогда при нормальном хранении этих данных в мапе с помощью ключ-значение, потребуется 150 записей.
Если в этой же мапе кроме этих значимых данных хранить еще пустые сущности, то потребуется уже 10.000 записей.  
То есть, эта карта будет хранить 98.5% ненужной информации.

Map должна хранить только значимые записи координата-entity
Пустое место на карте(земля) должно кодироваться отсутствием координаты в мапе.  
То есть, если координаты нет в мапе, то там должно быть пусто.

- Нарушение SRP, методы чужих ответственностей. 

Карта должна только хранить существа и обеспечить базовые операции с ними:  
Вставить, выдать одно существо и список всех хранимых существ, удалить.  
И методы, которые напрямую не управляют размещением существ, но необходимы для этого функционала:  
Сказать ширину/высоту карты и т.д.

Если какой-то метод не нужен для обеспечения хранения существ в карте, 
значит он не принадлежит к ответственности карты, а принадлежит к чужой ответственности.  

Здесь методы чужих ответственностей:  
🔸 Найти соседние координаты    
🔸 Сделать ход существом   

Наверное, для проекта в целом полезно иметь метод, который находит соседние координаты.  
Но этот процесс не имеет никакого отношения к единой ответственности карты- хранению существ в себе.  
Для организации хранения/удаления/выдачи существ, карте не нужно искать соседние координаты.

Методы чужих ответственностей должны находиться в тех классах, в интересах которых они работают.  
Если один и тот же метод используют разные классы, то метод нужно вынести в отдельный класс, например, "BoardUtils".

+ 👍 Хорошо, что геттеры не возвращают `null`, они возвращают `Optional`
```java

```

+ 👍 Хорошо, что возвращается копия мапы, а не оригинал.  
Тем самым соблюдается инкапсуляция и защищается внутреннее устройство класса

**6. class BFS**

- Этот класс не ищет путь.

Путь это последовательность точек от старта до финиша.  
Этот класс не ищет путь. Его единственный публичный метод возвращает одиночную координату
```java
public Coordinate getNextStepToFood(Creature eater)
```
Этот метод ищет не путь, а один шаг пути. Тоже хорошо конечно, но не то. 

Поиск пути должен просто искать путь от точки старта до точки, соответствующей заданным условиям согласно алгоритма BFS или A*.  
В случае алгоритма BFS- до точки, в которой находится существо нужного класса
```java
public class BfsPathFinder {
  public List<Coordinates> find(Карта карта, Coordinates start, Class<? extends Entity> target) {
  //ищет путь на карте от точки start
  //до точки, где находится существо нужного класса(напр. target == Grass.class)
  }
}
```

Или поиск должен искать путь между точками старта и финиша, согласно алгоритма A*
```java
public class AstarPathFinder {
  public List<Coordinates> find(Карта карта, Coordinates from, Coordinates to) {...}
}
```

Так же, поиск пути по алгоритму A* может использовать ту же сигнатуру, что и BFS.  
Тогда поиск пути в нем интерпретируется не как поиск пути между двумя точками, а как поиск цели и прокладывание пути к ней.  
Например: 
```java
public class AstarPathFinder {
  public List<Coordinates> find(Карта карта, Coordinates start, Class<? extends Entity> target) {
    //сначала находит координату цели
    //потом прокладывает путь по алгоритму A* между точкой старта и точкой цели
  }
}
```
Плюсы- унификация сигнатуры разных алгоритмов поиска для полиморфизма.  
То есть, можно сделать семейство родственных классов поиска, объединенных общим интерфейсом.

- Никогда не используй инструкцию `goto`
```java
outer:
while (!bfsQueue.isEmpty()) {
  for (Coordinate neighbor : field.getNeighbors(current)) {
    if (eater.canEat(entity)) {
      //...
      break outer;  <-- goto
    }
  }
}
```
Если программу нельзя написать без инструкции перехода на метку,
то это значит ТОЛЬКО ОДНО- алгоритм настолько запутанный, что нормальными способами его не распетлять.

Обычно так происходит потому, что метод большой и в нем куча вложенных друг в друга блоков.  
Разделяй такие большие методы на несколько вспомогательных.

**7. abstract class Entity**

- Нарушение SRP.

Искать свою координату существу нужно только с уровня ходящих существ- Creature
```java
public abstract class Entity {
  //...
  protected Coordinate getCurrentCoordinate(Field field) {...}
}
```
Другим потомкам- Камню и Дереву- не нужно узнавать свою координату.  
Поэтому этот метод должен находиться на уровне Creature.

Вообще, в иерархии классов все поля и методы должны появляться только на тех уровнях, где они используются и/или являются общими ДЛЯ ВСЕХ потомков.

- Нарушение SRP, зависимость модели от представления- существо хранит спрайт с собственным изображением
```java
public abstract class Entity {
  //...
  public abstract String getSprite();
}
```
Модель(а это модель) не должна зависеть от представления и знать, как ее будут показывать юзеру.  
Потому что в разных средах(консоль, Swing, Android) одна и та же модель может быть показана разными способами- пиксельной картинкой, анимацией etc.  
Спрайты всех существ должны храниться в классе, который распечатывает карту.

- Нарушение SRP.

Ожидание удаления существа не относится к ответственности самого существа
```java
private boolean pendingDespawn;
```

Условный пример:
На некотором предприятии каждого сотрудника поздравляют с др.  
Для этого ведется учет, поздравили его в этом году(true) или нет(false).  
Где должна храниться эта информация, на бумажке в кармане каждого сотрудника?  
Нет, она хранится в общем для всех сотрудников списке в отделе кадров.

То есть ответственность за контролем поздравления сотрудника лежит не на нём самом, а на ком-то другом.

**12. class Ecosystem**

- Что дало переименование указанного в ТЗ класса `Simulation` в `Ecosystem`? 🤷

- Нарушение конвенции кода.

Если в классе есть точка входа `main()`, то этот метод должен стоять самым первым среди методов.

- Нарушение SRP.

Класс с точкой входа `main()` должен только сконфигурировать зависимости и запустить программу.  
Управлять работой программы этот класс не должен.  

Метод `main()` нужно вынести в отдельный класс, который будет только собирать все зависимости и запускать программу.  

*Мартин, "ЧК", гл.11, "Отделение конструирования системы от ее использования"*

- Нарушение паттерна GRASP "Creator"(Создатель)

Здесь класс принимает в конструктор зависимость, которую должен создавать самостоятельно:
```java
public Ecosystem(Field field, ConsoleRenderer renderer) {...}

//ПРАВИЛЬНО:
public Ecosystem(Field field) {
  this.renderer = new ConsoleRenderer(field);
  //...
}
```
Creator гласит, что создавать объект должен тот, кто его использует. 

Рассмотрим, что это значит.

В данном случае `Ecosystem` принимает в конструктор `Field field`- это правильно.  
Потому что карта может быть создана разных размеров и `Ecosystem` не знает, какая именно карта нужна в этот раз.  
Поэтому ее создает клиент, а потом инжектит в этот класс.

Но принимать в конструктор `ConsoleRenderer`- уже неправильно.  
Потому что `ConsoleRenderer` это конкретный класс, а не интерфейс и этот класс не параметризируется. 

Экземпляр `ConsoleRenderer` всегда одинаковый.  
Поэтому, согласно паттерну Creator, объект `ConsoleRenderer` *здесь* должен создавать сам класс `Ecosystem`.

Технически, можно создать наследника `ConsoleRenderer`, переопределить в нем методы и передавать в конструктор `Ecosystem`.  
Но если программист хочет использовать в своем классе другие классы через полиморфизм, то он должен обозначить свои намерения более явно.  
Например, передавая в конструктор интерфейс или абстрактный класс.

- Неправильное использование потоков в проекте.

Внутри класса Simulation/Ecosystem не должно быть никакой работы с потоками
```java
private Thread simulationThread;

public void start() {
  //...
  simulationThread = new Thread(() -> {...}

  simulationThread.setName("ecosystem-simulation-thread");
  simulationThread.start();
}
```

Этот класс не должен управлять потоками.  
Наоборот, какие-то потоки должны управлять этим классом и дергать за его публичные методы, которые указаны в ТЗ:
```java
Simulation #
Главный класс приложения, включает в себя:
...
nextTurn() - просимулировать и отрендерить один ход
startSimulation() - запустить бесконечный цикл симуляции и рендеринга
pauseSimulation() - приостановить бесконечный цикл симуляции и рендеринга
```

Это должен быть такой класс, который можно будет не только запускать из потоков.  
Но и запустить без потоков просто в бесконечном цикле и он должен(бесконечно) работать:
```java
public class Main {
  public static void main(String[] args) {
    GameMap gameMap = new GameMap(10, 10);
    //...
    Simulation simulation = new Simulation(gameMap, ...);
    simulation.startSimulation(); //бесконечная симуляция без потоков 
  }
}
```

Для этого класс должен выглядеть примерно так:
```java
public class Simulation {
  //...

  public Simulation(...) {
    //выполняет все initActions
  }

  public void nextTurn() {
    //выполняет все turnActions
    //печатает карту
    //печатает сопроводительную информацию: n.хода и прочее
  }

  public void startSimulation() {
    isRunning = true;
    while(isRunning) {
      nextTurn();
      sleep();
    }
  }

  private void sleep() {
    try {
      Thread.sleep(SLEEP_TIME);
    } catch (InterruptedException e) {...}
  }

  public void pauseSimulation() {
    //останавливает бесконечный цикл
  }
}
```

Когда мы добавляем в программу потоки, то поток должен принимать команды от юзера и дергать `Simulation` за ее методы:   
`nextTurn()`, `startSimulation()` и `pauseSimulation()`.

**Для тренировки можно сделать два Main'a в проекте.**  
По запуску одного симуляция должна работать так, как сейчас- с возможностью делать паузу/пуск.  
А другой Main должен работать без команд пауза/пуск в режиме бесконечной симуляции.  
И выглядеть должен примерно так:
```java
public class MainWithoutThreads {
  public static void main(String[] args) {
    GameMap gameMap = new GameMap(10, 10);
    //...
    Simulation simulation = new Simulation(gameMap, ...);
    simulation.startSimulation(); //бесконечная симуляция без потоков 
  }
}
```
